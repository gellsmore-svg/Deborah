### Functional defects

#### F1. Ordinary English at the start of a step is captured as a construct, and the word is deleted

This is the most consequential finding in the review. Construct matching is
**case-insensitive** (`re.I`), so any step whose prose begins with a construct
keyword is silently re-typed and loses its first word.

```
$ deborah-render demo.cairn.md --profile narrative_steps
source:   1. Step one.                          rendered:  1. one.
source:   4. Step through the queue carefully.  rendered:  4. through the queue carefully.
source:   2. Stage the payload.                 rendered:  2. Stage the payload.   (unaffected)
```

Through the full library path the step also changes **type**:

```python
>>> doc = deborah.parse_document("PROCESS — T.\n  1. Role clarity improves retention.\n")
>>> deborah.document_to_plan(doc)["steps"][0]
{'id': 's1', 'action': 'clarity improves retention.', 'construct': 'ROLE', …}
>>> deborah.validate_document(doc)
[]        # clean — nothing warns
```

Verified captures, all from plain prose: `Call the customer back.` → `CALL`,
`Error handling is manual.` → `ERROR`, `Role clarity improves retention.` →
`ROLE`, `Conflict is unresolved.` → `CONFLICT`, `Feedback was positive.` →
`FEEDBACK`, `Vision statements need review.` → `VISION`, `Service the boiler.` →
`SERVICE`, `Break the bad news gently.` → `BREAK`, `Queue the applicants fairly.`
→ `QUEUE` (whose text is then replaced wholesale by generated queue boilerplate).

The affected keywords are precisely the **descriptive / human-systems**
constructs the README names as the point of the language — `ROLE`, `VISION`,
`CONFLICT`, `FEEDBACK`, `COALITION`, `RESISTANCE`. Those are among the most
common nouns in exactly the psychological, organisational and sociological
documents Deborah is pitched at. A retrospective or change-management process
will be silently mis-parsed, mis-typed, and mis-rendered, and
`validate_document` will call it clean.

Root cause in H2.

#### F2. The bounded-loop rule fires on the syntax the SPEC documents

`SPEC.md:461` gives the formal syntax as `ITERATE [UNTIL: <condition>; MAX: <n>]`.
That form is rejected:

| where the bound is written | result |
|---|---|
| `ITERATE [UNTIL: consensus; MAX: 10] → CALL Critic(draft) [LLM]` | **FLAGGED** — "must declare MAX or UNTIL" |
| `ITERATE → CALL Critic(draft) [LLM] [MAX: 10]` (trailing tag) | ok |
| bound on an indented sub-line | **FLAGGED** |

Only the trailing-tag form is recognised. This is the language's single most
safety-critical rule — unbounded stochastic loops — producing false positives on
its own documented notation.

It is why four bundled examples fail `deborah-validate`:

```
examples/mahalath.cairn.md                 ITERATE with LLM involvement must declare MAX or UNTIL
examples/round-robin-debate.cairn.md       QUEUE   with LLM involvement must declare MAX or UNTIL
examples/tirzah-recursive-planning.cairn.md RECURSE with LLM involvement must declare MAX_DEPTH or UNTIL
examples/tirzah.cairn.md                   ITERATE with LLM involvement must declare MAX or UNTIL
```

All four **do** declare their bounds:

```
round-robin-debate.cairn.md:34   2. QUEUE [ORDER: ROUND_ROBIN; ONE_AT_A_TIME; ROUNDS: 5; UNTIL: consensus; MAX: 10]
tirzah.cairn.md:105              1. ITERATE [UNTIL: decision.status = done; MAX: memory_agent_max_iterations] [SATISFIES: R6]
```

`tests/test_grammar.py:197-210` allow-lists these four files with the comment
*"pre-existing LLM bound issues in old examples"* — attributing a validator bug
to the authors. See M4 for why that allow-list is worse than it looks.

Root cause in H3 (one line).

#### F3. `narrative_steps` merges separate processes into one flat list

`examples/hoglah.cairn.md` defines **five** named PROCESS blocks — `RunBridge`,
`Ingest`, `Work`, `Egress`, `RecoverOnStartup`. The rendered view emits **one**
heading and concatenates all five beneath it:

```
## RunBridge

1. On startup, CALL RecoverOnStartup(Store, broker).
2. CONCURRENT
1. Consume the next message from the broker.        ← Ingest starts, no heading, no indent
2. Parse / validate into a JobRequest.
3. Enqueue durably in Store.
  **State Update:** Store += job (no-op if correlation_id already present)
4. Ack / commit the broker offset.
1. Claim next QUEUED job: atomic QUEUED → PROCESSING.   ← Work starts, numbering resets again
2. Retry:
  2. 1 Execute the model call within timeout.        ← mangled number join ("2. 1")
```

A reader cannot tell where one process ends and the next begins; the numbering
resets four times inside what reads as a single list; the `SERVICE IngestLoop /
WorkLoop / EgressLoop` branch labels under `CONCURRENT` are gone; and the only
indentation present (`**State Update:**`) is inconsistent with the structure it
sits in. Identical output via the CLI and `POST /api/render`, so this is the core
renderer, not a CLI wrapper.

For a package whose stated primary goal is *"maximum human readability"* and
whose ultimate test is *"a reader thinks 'I get what's happening here'"*, the
flagship profile loses the document's hierarchy.

#### F4. A documented `--slice` invocation reads stdin instead of the example

`docs/PROCESS-SEMANTICS-AND-ROADMAP.md:352` documents:

```bash
deborah-run --slice --open-questions PATH --question "…"
```

With no positional input, `cli.py:189` falls through to `sys.stdin.read()`. From
a pipe that yields an empty document and a confusing grammar error:

```
$ deborah-run --slice --question "What is a vorton?" --estate-demo
document must contain at least one CONTEXT, REQUIREMENTS/OUTCOMES, or PROCESS block
```

From an interactive terminal it hangs waiting for input. Every other doc
(`usage-modes.md`, `GUIDE-HUMAN.md`, the example itself) passes the file
explicitly and works. Either default `--slice` to the bundled slice plan or fix
the one doc line.

#### F5. `CANONICAL_PLAN` — the advertised known-good fixture — fails `strict`

The README documents both `deborah.CANONICAL_PLAN  # known-good fixture` and
`validate_plan(plan_dict, profile="strict")`:

```
CANONICAL_PLAN  full  : CONFORMANT
CANONICAL_PLAN  strict: ["step[1] strict: CALL tool 'Synthesise' not in assumes
                         ['answer_adapter', 'retrieval']"]
```

Either the fixture needs `Synthesise` in `assumes`, or `strict`'s CALL-tool rule
is wrong. As shipped, the reference plan does not satisfy the strictest profile
the package offers.

#### F6. `POST /api/render` returns a confident empty success on a bad payload

`web.py:392` does `str(payload.get("source", ""))`. A client sending any other
key — or omitting it — gets:

```json
{"ok": true, "output": "", "format": "markdown", "warnings": [], "line_count": 0}
```

No error, no warning. Identical response for a valid document under the wrong key
and for total garbage, so a caller cannot tell "your document rendered to
nothing" from "you sent the wrong field". (The bundled UI sends `source`
correctly, so the composer itself works — this bites API consumers only.)

## Part 2 — Code review

### High

#### H1 · `runtime/interpreter.py:125` — the allow-list is bypassable by substring

```python
if stem not in allow and not any(stem in a or a in stem for a in allow):
```

A **bidirectional** substring test. With `assumes = ["tirzah.retrieve@1",
"milcah.critique@1"]`:

```
ALLOWED   tirzah.retrieve            ← intended
ALLOWED   milcah.critique            ← intended
ALLOWED   z                          ← single char, substring of "tirzah.retrieve"
ALLOWED   a
ALLOWED   ret
ALLOWED   evilmilcah.critique        ← allowed name is a substring of the caller
ALLOWED   milcah.critique.exfiltrate ← arbitrary extension of an allowed name
blocked   attacker.tool              ← only names sharing no substring are blocked
```

The module docstring names the allow-list as one of the four things this runtime
guarantees ("order, allow-list, bounds, terminals"). Nearly any short tool name
passes, and any name that *contains* an allowed capability passes. Combined with
F2/H3, two of the four stated guarantees do not hold.

**Fix:** compare normalised identifiers — exact match on the `@`-stripped stem,
or an explicit namespace rule (`stem == a or stem.startswith(a + ".")`). Never
`in`.

#### H2 · `grammar/parser.py:55-66` — construct matching is case-insensitive against free prose

`_CONSTRUCT_LINE` and `_CONSTRUCT_STEP` are both compiled with `re.I`:

```python
_CONSTRUCT_STEP = re.compile(
    r"^(STEP|MILESTONE|ITERATE|RECURSE|QUEUE|PARALLEL|SERVICE|DECISION|RETRY|ERROR|AWAIT|CALL|"
    r"…|ROLE|FEEDBACK|MACRO)\b(.*)$",
    re.I,
)
```

```
'Step one.'                 -> CONSTRUCT=Step  body=' one.'
'Call the customer back.'   -> CONSTRUCT=Call  body=' the customer back.'
'Error handling is manual.' -> CONSTRUCT=Error body=' handling is manual.'
'Stage the payload.'        -> no match
```

Constructs are an upper-case notation everywhere in `SPEC.md` and `GRAMMAR.md`.
Matching them case-insensitively against prose is what produces F1, and it is
load-bearing for parse, validate, plan export and render simultaneously.

**Fix:** drop `re.I` from both patterns. If mixed case must be tolerated for
authoring convenience, require the keyword to be followed by a modifier bracket
or `→` before treating it as a construct.

#### H3 · `grammar/validate.py:524` — the step's own modifiers are discarded

```python
def _check_iteration_bound(step: Step, lineno: int) -> list[str]:
    for cline in step.construct_lines:
        parsed = getattr(cline, "parsed_modifiers", {}) or {}
        if _has_iteration_bound(cline.modifiers, cline.text, [], parsed):   # ← correct
            return []
    if _has_iteration_bound([], step.text, step.tags):                      # ← drops both
        return []
```

The construct-line branch threads `modifiers` and `parsed_modifiers` through; the
step branch passes `[]` and omits `parsed_modifiers` entirely — even though the
parser populated them (`parser.py:453-458`). Demonstrated on
`ITERATE [UNTIL: consensus; MAX: 10] → CALL Critic(draft) [LLM]`:

```
step.modifiers        : ['UNTIL: consensus; MAX: 10']
step.parsed_modifiers : {'UNTIL': 'consensus', 'MAX': '10'}
current  _has_iteration_bound([], step.text, step.tags)              -> False
with the step's own modifiers passed through                          -> True
```

**Fix:** one line —
`_has_iteration_bound(step.modifiers, step.text, step.tags, step.parsed_modifiers)`.
Then remove the four entries from the `known_issues` allow-list (M4).

#### H4 · `conformance.py` — `validate_plan` does no graph validation, and the interpreter silently repairs what it finds

Against `CANONICAL_PLAN`, with the baseline errors subtracted:

```
ACCEPTED  duplicate step ids
ACCEPTED  depends_on a missing step
ACCEPTED  self-dependency
ACCEPTED  cycle s1 <-> s2
ACCEPTED  negative max_steps
ACCEPTED  revision = 'abc'
```

`interpret_plan` then runs the cyclic plan without comment —
`_ready_order` (interpreter.py:203-207) detects the cycle, falls back to sorted
id order, and reports nothing:

```
validate_plan : CONFORMANT
terminal      : complete
executed order: ['s1', 's2']
errors        : []            # the cycle is invisible
```

So a plan with violated dependencies validates clean, executes to `complete`, and
leaves no trace that its ordering constraints were ignored. `validate_plan` is
the contract Tirzah's planner is tested against (README, `PLAN-OWNERSHIP.md`), so
this is the seam where a malformed generated plan would be caught — and it isn't.

**Fix:** add id-uniqueness, dangling-`depends_on`, self-dependency and cycle
checks to `validate_plan`; make `_ready_order` push an error/event instead of
silently reordering.

### Medium

```
338:  from tirzah.deborah import deborah_dispatch as tirzah_dispatch
344:  from milcah.deborah import deborah_dispatch as milcah_dispatch

#### M2 · `manifest.py` — the manifest still does not advertise the runtime

```

advertises the interpreter? False

`deborah-run` is a console script and the interpreter is 511 lines, but an MCP

#### M3 · `render/` — hierarchy and numbering (F3's code side)

Multiple PROCESS blocks collapse under a single heading, nested/branch content
renders at zero indentation with numbering restarting per block, and compound
step ids join as `"2. 1"` rather than `2.1`. Any of the three alone is a bug; the
combination makes a multi-process document unreadable in the profile most likely
to be shown to a non-technical reader.

#### M4 · `tests/test_grammar.py:197-210` — the allow-list hides a bug and suppresses future real ones

```python
known_issues = {"mahalath.cairn.md", "round-robin-debate.cairn.md",
                "tirzah-recursive-planning.cairn.md", "tirzah.cairn.md"}
…
    # pre-existing LLM bound issues in old examples; domain is clean
    wf = [e for e in wf if "must declare MAX" not in e and "MAX_DEPTH" not in e]
```

Two problems beyond the misattribution. It filters on the **error string**, not
on a specific known occurrence — so any *genuine* unbounded-LLM-loop introduced
into those four files from now on is silently swallowed. And it has no expiry, so
the validator bug had no pressure to surface. These are the reference documents
for Tirzah and Mahalath — the files a newcomer is most likely to read.

**Fix:** land H3, delete the allow-list, and add a test asserting that the
SPEC's `ITERATE [UNTIL: …; MAX: …]` form validates.

#### M5 · `runtime/interpreter.py:158-164` — the tool name is inferred from the action's first word

```python
if (step.get("construct") or "").upper() == "CALL" and not tools:
    action = str(step.get("action") or "")
    …
    tools.append(parts[0])
```

For a `CALL` step without `allowed_tools`, the allow-list decision is made from
whatever word happens to start the prose. Given H2 has *already removed* the
first word from some actions, the token checked against the allow-list may not be
the token the author wrote. Require `allowed_tools` on `CALL`, or parse the
callee syntactically.

#### M6 · `runtime/interpreter.py:171-178` — absent `assumes` means unrestricted

`_allow_list_from_plan` returns `None` (no restriction) when `assumes` is missing
or empty. Default-open is a defensible choice for a language tool, but it should
be an explicit, logged decision rather than a silent fallthrough — especially
given H1 means the non-empty case is weak too.

#### M7 · `web.py:392` — silent default on a missing field (F6's code side)

`str(payload.get("source", ""))` cannot distinguish absent from empty. Return a
400 when `source` is missing, and set `ok: false` when the document produced no
renderable content.

### Low

#### L1 · `runtime/interpreter.py:209-211` — dict-equality membership test

```python
for s in steps:
    if isinstance(s, dict) and s not in ordered:
        ordered.append(s)
```

`s not in ordered` compares dicts by **value**, so two structurally identical
id-less steps collapse into one, and the check is O(n²). Track ids in a set.

`pytest.skip` when unreachable — so this machine ran 0 skips while CI, which has
no estate, silently runs a smaller suite. Worth reporting the skip count in CI so
the difference is visible rather than assumed.

## Comparison with the Hoglah review

The same pattern names both codebases, from opposite directions.

In Hoglah the failures clustered where **a heuristic substituted for a structured
signal** — substring matching on error text, on output text, `LIKE` on JSON.

In Deborah the failures cluster where **a matcher is too permissive about
identity**: `re.I` on construct keywords (H2), bidirectional `in` on the
allow-list (H1), value-equality on dicts (L1). Each one accepts things it should
not, and each is silent when it does.

The mirror-image finding is H3/F2 — a matcher that is too *strict* in one place
(only trailing-tag bounds count) — and the response was to widen the test rather
than fix the matcher. That is the one habit worth changing deliberately: an
allow-list in a test is a decision to stop being told about a class of error.

## Suggested order

1. **H2** (drop `re.I`) and **H3** (one-line modifier passthrough) — two small
   changes that between them fix F1, F2, and clear four bundled examples. Land
   H3 with **M4** (delete the allow-list) in the same commit.
2. **H1** — the allow-list is the runtime's stated safety boundary and currently
   is not one. Small, local, high value.
3. **H4** — graph validation in `validate_plan` plus a reported cycle in
   `_ready_order`. This is the seam Tirzah's planner is checked against.
4. **F5, F4, M7, M2** — four small correctness/consistency fixes with no design
   question attached.
5. **M3/F3** — the renderer needs a hierarchy design decision, not a patch.
6. **M1** — Keturah-mediated dispatch; the largest change and the least urgent.

The architecture is sound and the slice is real working evidence for the
crystallisation thesis. Nothing here is structural: the four High findings are
one regex flag, one argument list, one comparison operator, and a missing
validation pass.
